# Nippan AI Platform — สรุปโปรเจกต์ฉบับเต็ม (ให้ทีม AI อ่าน)

## 🔴 สถานะเดียวที่ต้องจำ — อ่านก่อนทุกหัวข้ออื่น

**ตอนนี้อยู่ในช่วง "สร้างระบบ" ยังไม่ใช่ช่วง "ใช้งานจริง"**

- **ลูกค้าจริง = ศูนย์** ไม่มีร้านค้าไหนใช้บอทนี้อยู่จริงเลยแม้แต่รายเดียว
- **บอทที่ลูกค้าคุยได้จริงบน LINE แบบครบวงจร = ยังไม่มี** (ยังไม่มีโค้ดส่วนนี้)
- สิ่งที่มีจริงแล้วคือ **"โครงสร้างพื้นฐานเบื้องหลัง"** เช่น ฐานข้อมูล, การทดสอบแยกข้อมูลร้าน, เครื่องมือทีมภายใน — **สิ่งเหล่านี้คือส่วนประกอบที่ยังไม่ได้ประกอบเป็นสินค้าที่ลูกค้าใช้ได้**

**เปรียบเทียบ:** เหมือนสร้างบ้าน — ตอนนี้มีฐานราก มีท่อน้ำ มีสายไฟวางไว้แล้ว (โครงสร้างพื้นฐาน) แต่**ยังไม่มีผนัง หลังคา หรือประตูให้คนเข้าอยู่ได้จริง** (สินค้าที่ลูกค้าใช้) ห้ามพูดว่า "บ้านเสร็จแล้ว" เพียงเพราะมีฐานรากกับท่อน้ำ

**กฎสำหรับ AI ทุกตัว:** ถ้างานที่ได้รับมอบหมายฟังดูเหมือนต้องเกี่ยวกับ "ลูกค้าจริง" หรือ "ข้อมูลลูกค้าจริง" — หยุดและถามก่อน เพราะไม่ควรมีอยู่ตอนนี้ นี่คือสัญญาณว่าอาจเข้าใจสถานะผิด ไม่ใช่ว่าลูกค้ามีจริงแล้ว

---

เอกสารนี้คือคำอธิบายทั้งโปรเจกต์แบบเล่าเรื่อง ให้ AI ที่เพิ่งเข้ามาทำงานอ่านแล้วเข้าใจภาพรวมทันที โดยไม่ต้องไล่เปิดไฟล์ทีละไฟล์ก่อน

**สำคัญ:** นี่คือสรุป ไม่ใช่แหล่งความจริง ถ้าเนื้อหาขัดกับไฟล์ใน repo (branch `phase-a-market-test-pivot`) ให้ยึดไฟล์ใน repo เป็นหลัก โดยเฉพาะ `docs/warroom/AI_OPERATING_PROTOCOL.md` ที่บังคับทุกตัว

## 1. เราทำอะไร ทำไมทำแบบนี้

**สิ่งที่ทำ:** ให้ร้านค้า/ธุรกิจขนาดเล็กในไทย "เช่า" บอท AI ไปใช้ตอบลูกค้าผ่าน LINE ของร้านเอง หรือแชทบนเว็บ ราคา 299 บาท/บอท/เดือน ราคาเดียว ไม่มีชั้นราคาซับซ้อน

**ทำไมต้อง 30 ร้านก่อน ไม่ทำใหญ่เลย:** โครงการนี้เคยมีแผนใหญ่มาก่อน (สถาปัตยกรรมระดับ FastAPI + Cloudflare + PostgreSQL/pgvector รองรับ 100+ ร้าน) แต่พบว่าเขียนเอกสารเยอะมาก โค้ดจริงแทบไม่มี — จึงตัดสินใจ **หันมาทดลองตลาดเล็กก่อน** ด้วยสถาปัตยกรรมที่เบากว่ามาก คือ **n8n** เป็นแกนกลาง เพื่อพิสูจน์ว่าร้านเล็กจะจ่ายเงินจริงไหม ก่อนลงทุนสร้างระบบใหญ่

**แผนเดิมไม่ได้ทิ้ง** ทั้งหมดถูกเก็บไว้ที่ `docs/future/` เป็น "พิมพ์เขียว" สำหรับตอนขยายไปเฟส C ในอนาคต — สำคัญมาก: **ห้ามหยิบอะไรจากโฟลเดอร์นั้นมาใช้ตอนนี้** จนกว่าเงื่อนไขใน `docs/future/README.md` จะบอกว่าถึงเวลา

**คำเตือนที่ AI ต้องรู้:** ที่ผ่านมาโปรเจกต์นี้เคยมีปัญหา "เขียนเอกสารเยอะ แต่ของจริงสร้างน้อย" — ทุกงานที่ AI ทำต้องแยกให้ชัดว่า "ออกแบบไว้แล้ว" กับ "สร้างจริงแล้วใช้งานได้" เป็นคนละเรื่องกัน ห้ามสับสนสองอย่างนี้

## 2. สถาปัตยกรรม — รูปร่างระบบ

```
ลูกค้าของร้าน → LINE ของร้านเอง / แชทบนเว็บ
                       ↓
         n8n (ติดตั้งเซิร์ฟเวอร์ของเราเอง ไม่ใช่บริการเช่า)
         ↙                                    ↘
   เครื่องมือ MCP                      ฐานข้อมูล PostgreSQL (lite schema)
  (ตอบแชท, ความจำ,                    tenants → bots → channels →
   ตั้งค่า, นับการใช้,                  end_customers → conversations
   แจ้งเตือน, ส่งต่อ)
```

**ทำไมใช้ n8n ไม่ใช้ FastAPI แบบแผนเดิม:** n8n ติดตั้งเองได้ ใช้ลาก-วางสร้าง workflow ไม่ต้องเขียนโค้ดเยอะ เหมาะกับทีมเล็กและ scale 30-60 ร้าน — FastAPI/Cloudflare Worker เก็บไว้ใน `docs/future/` รอตอนขยายจริง

**โครงฐานข้อมูล (lite schema) — จุดสำคัญที่สุดที่ AI ต้องเข้าใจ:**
ลำดับชั้นคือ **ร้าน (tenant) → บอท (bot) → ช่องทาง (channel) → ลูกค้าของร้าน (end_customer) → บทสนทนา (conversation)**

- หนึ่งร้านมีได้หลายบอท (จ่ายเพิ่มต่อบอท) — เพราะงั้น**ทุกตารางที่เก็บข้อมูลลูกค้า ต้องมีทั้ง `tenant_id` และ `bot_id` กำกับเสมอ ไม่มีข้อยกเว้น** ถ้า AI เขียน workflow ที่ query ข้อมูลโดยไม่ใส่ทั้งสองรหัสนี้ ถือว่าผิดกฎเหล็ก เพราะข้อมูลร้าน/บอทจะปนกัน

**ความจำ 4 ชั้น:**
1. บทสนทนาปัจจุบัน (จำกัดจำนวนแถวล่าสุด ไม่ใช่ทั้งหมด)
2. สรุปย่อ (งานตามรอบ ย่อยข้อมูลเก่าเป็นสรุปสั้น)
3. ความจำระยะยาว ค้นหาด้วยคำ (ยังไม่ใช้ vector search ในเฟสนี้)
4. ข้อมูลธุรกิจถาวร (ราคา เวลาเปิด ฯลฯ — เป็น config ไม่ใช่ความจำจริงๆ)

ทุกแถวความจำระยะยาวต้องมี **วันหมดอายุ (`expires_at`)** บังคับ ตามกฎ PDPA ด้านล่าง

## 3. LINE — กลไกที่ AI มักเข้าใจผิด (สำคัญมาก)

**Reply message** (บอทตอบข้อความที่ลูกค้าทักมาก่อน) = **ฟรี ไม่จำกัดจำนวน** ใช้ reply token ครอบคลุมงานหลักคือบอทตอบแชททั้งหมด

**Push message** (บอทเป็นฝ่ายเริ่มส่งเอง เช่น เตือนนัดล่วงหน้า) = มีเพดานของ LINE เอง (แพ็กเกจฟรี 300 ข้อความ/เดือน) **เรากำหนดนโยบายของเราเองให้จำกัดไว้ที่ 200 ข้อความ/เดือนต่อบอท** ต่ำกว่าเพดานจริงของ LINE เพื่อกันไม่ให้ร้านโดนเก็บเงินเองโดยไม่รู้ตัว

**แต่ละร้านต้องใช้ LINE OA ของร้านตัวเอง** ห้ามใช้บัญชี LINE กลางบัญชีเดียวสำหรับทุกร้าน เพราะจะคุมโควตาแยกรายร้านไม่ได้และต้นทุนจะกินกำไรทั้งหมด

## 4. กฎเหล็กที่ AI ห้ามละเมิดเด็ดขาด

1. **ห้ามบอกว่าใช้ AI ยี่ห้อไหน** ไม่ว่าลูกค้าจะถามตรงหรือถามอ้อม
2. **แต่ห้ามแกล้งเป็นคน** — ถ้าลูกค้าถามจริงจังว่าคุยกับคนหรือบอท ต้องยอมรับว่าเป็นผู้ช่วยอัตโนมัติ (สองข้อนี้คนละเรื่องกัน ไม่ขัดแย้งกัน)
3. **ห้ามเอาข้อมูลบทสนทนาลูกค้าไปเทรน/ฝึกโมเดลใดๆ** โดยไม่ได้รับความยินยอมแยกต่างหากล่วงหน้า — นี่คือสาเหตุอันดับ 1 ที่ธุรกิจ AI ไทยโดนร้องเรียนเรื่อง PDPA
4. **ข้อมูลแต่ละร้านห้ามปนกันเด็ดขาด** (ดูข้อ 2 เรื่อง tenant_id + bot_id)
5. **บอทตอบราคา/สต็อก/นโยบายจากข้อมูลร้านเท่านั้น** ไม่แน่ใจให้ส่งต่อเจ้าของร้าน ห้ามเดา

## 5. War Room — ทีมงานที่บอทและระบบใช้

**ตำแหน่งคงที่ ตัว AI ที่นั่งเปลี่ยนได้** ห้าม hardcode ชื่อโมเดลลงในโค้ด/ระบบ ต้องผ่านนโยบายเลือกโมเดลเสมอ

| ตำแหน่ง | หน้าที่ |
|---|---|
| Project Lead (ตอนนี้คือเจ้าของโครงการ) | ตัดสินใจสุดท้าย อนุมัติ ถือบันทึกการตัดสินใจ |
| Developer / MCP tool builder | สร้าง workflow และเครื่องมือ |
| Auditor | ตรวจก่อนถึงลูกค้าจริง — **ต้องเป็นคนละตัวกับที่สร้างงาน** |
| Cost Guard | คุมต้นทุนเท่านั้น (ไม่ใช่มอนิเตอร์ทั้งระบบ) |
| Onboarding / Support | ตั้งค่าบอทร้านใหม่ ดูแลร้านเดิม |
| Marketing | เก็บสัญญาณตลาด ร่างการตลาด |
| Model Scout | หา AI ยี่ห้อใหม่ที่ถูกกว่า/ดีกว่า **เสนอเท่านั้น ไม่สลับเอง** |

**บันไดความอิสระ 4 ขั้น** (ทุกตำแหน่ง): ทำมือ → AI ร่างให้คนตัดสิน → AI ทำเองเรื่องปกติ → AI ทำเองคนดูสรุป — ทำพลาดร้ายแรงลงทันที 1 ขั้น เริ่มต้นตอนนี้ Operations อยู่ขั้น 2 ที่เหลือขั้น 1

## 6. ระบบควบคุมงาน — วิธีที่ AI ทุกตัวต้องทำงาน (สำคัญที่สุดสำหรับทีม AI)

**ทุกงานต้องอยู่ใน `TASKS.md`** ไม่มีงานไหนอยู่แค่ในแชท เพราะ AI แต่ละตัว/แต่ละ session จำกันไม่ได้

**ก่อนเริ่มงานใดๆ ต้องเขียน "รายงานรับงาน" ก่อน** แล้วตัดสินใจอย่างใดอย่างหนึ่ง: **รับ / รับบางส่วน / ปฏิเสธ / ให้เจ้าของตัดสิน** — การปฏิเสธตรงๆ ไม่ใช่เรื่องผิด ถือว่า**ถูกต้อง**

**บังคับต้องปฏิเสธ** ถ้า: ไม่มีสิทธิ์เข้าถึงสิ่งที่ต้องใช้ / ทดสอบผลไม่ได้ / ต้องเดาข้อเท็จจริง / ประเมินแล้วใช้เวลาเกิน 2 เท่าของงบ / รู้ตัวว่าไม่ถนัดงานนั้น

**ความเสี่ยง 3 ระดับกำหนดว่าต้องตรวจแค่ไหน:**
- L1 (ปกติ กลับตัวได้) — ทำแล้วเช็คเอง
- L2 (กระทบลูกค้าจริง) — ต้องผ่าน Auditor + เจ้าของอนุมัติ
- L3 (แก้ยาก เช่น ราคา, PDPA, ฐานข้อมูล, กฎหน้าบ้าน) — ต้องมี Auditor + อนุมัติ + บันทึกเหตุผลในบันทึกการตัดสินใจ

**"เสร็จ" ต้องมีหลักฐานทุกเงื่อนไข** ถ้าเงื่อนไขไหนพิสูจน์ไม่ได้ สถานะต้องเป็น **"เสร็จบางส่วน"** ห้ามเขียนว่าเสร็จโดยไม่มีหลักฐาน — **นี่คือความผิดร้ายแรงที่สุดในระบบนี้**

**การตรวจรับต้องเป็น AI คนละตัว หรือเจ้าของเอง** ไม่ใช่ตัวที่สร้างงานตรวจงานตัวเอง

**จำกัดงานพร้อมกันไม่เกิน 3 งาน** และถ้าใช้เวลาเกิน 2 เท่าของงบต้องหยุดรายงาน ห้ามดันทำต่อ

**เอกสารกฎหลักเหล่านี้แก้ได้เฉพาะแบบ L3 เท่านั้น:** ราคา, กฎหน้าบ้าน, PDPA, โครงฐานข้อมูล, สัญญาการเชื่อมต่อ, บทบาท War Room, ระเบียบการทำงาน AI, นโยบายทำงาน

## 7. การเชื่อมต่อแพลตฟอร์มภายนอก — ปัจจุบันและอนาคต

**หลักการเดียว: แกนกลางไม่รู้จักแพลตฟอร์มใดเลย** ทุกแพลตฟอร์ม (ที่มีตอนนี้และที่ยังไม่เกิด) เข้าผ่าน **"อะแดปเตอร์"** 1 ตัวที่แปลงเป็นรูปแบบกลางเดียวกันเสมอ แพลตฟอร์มใหม่ = เขียนอะแดปเตอร์เพิ่ม 1 ตัว **ไม่แตะแกนกลาง**

อะแดปเตอร์มี 3 แบบ: **ช่องทางแชท** (LINE ที่มีแล้ว, Facebook, WhatsApp ในอนาคต) · **ตัวเชื่อมระบบร้าน** (POS, ปฏิทิน, บัญชี) · **แหล่งเหตุการณ์** (เงินเข้า, มีออร์เดอร์ใหม่)

บอทขอ **"ความสามารถ"** ไม่ใช่ **"แพลตฟอร์ม"** เช่น "เช็คสต็อก" ทำงานเหมือนกันไม่ว่าร้านใช้ POS ยี่ห้อไหน — นี่คือที่มาของความยืดหยุ่นที่ต้องการ

**ยังไม่สร้างอะแดปเตอร์ใหม่ล่วงหน้า** สร้างเมื่อร้านร้องขอจริงเท่านั้น (ผ่านฝ่ายการตลาดเก็บสัญญาณ)

## 8. PDPA — สถานะทางกฎหมาย

**ร้านที่เช่าบอทเป็น "ผู้ควบคุมข้อมูล"** ส่วนแพลตฟอร์มของเราเป็น **"ผู้ประมวลผลข้อมูลแทน"** — ต้องเขียนไว้ในสัญญาชัดเจน

ต้องมี: ข้อความแจ้งความยินยอมอัตโนมัติตอนลูกค้าเริ่มแชทครั้งแรก / ระบบลบข้อมูลอัตโนมัติตามอายุ / ทางให้ลูกค้าขอลบข้อมูลตัวเองได้จริง

**สัญญากับร้านยังต้องให้ทนายตรวจก่อนรับลูกค้าจริง** — เป็นเงื่อนไขบังคับ ยังไม่ใช่แค่คำแนะนำ

## 9. สถานะตอนนี้ (สำคัญมาก — อย่าเข้าใจผิด)

แยกให้ชัดเป็น 2 เรื่อง เพราะเป็นคนละเรื่องกันแต่มักถูกปนกันจนงง:

### เรื่อง A — สินค้าที่ลูกค้าใช้ (แทร็กลูกค้า) — ยังไม่มีอะไรจริงเลย

- ไม่มีบอทที่ตอบลูกค้าจริงบน LINE แบบครบวงจร (รับข้อความ → ตอบ → จำบริบท → ส่งต่อเจ้าของร้านเมื่อไม่มั่นใจ)
- ไม่มีร้านค้าไหนสมัครใช้งานจริง
- ไม่มีช่องทางแจ้งเตือนเจ้าของโครงการเมื่อระบบมีปัญหา (โค้ดที่เขียนไว้ยังข้ามเงียบเมื่อไม่มีช่องทาง ไม่เคยส่งถึงใครจริง)
- ไม่เคยทดสอบ backup/restore กับฐานข้อมูลจริงที่ใช้งานอยู่ (ทดสอบแค่ในเครื่อง)
- ด่าน PDPA (ข้อความยินยอม, เส้นทางลบข้อมูล, สัญญาผู้เช่า) ยังไม่ทำจริง แค่ออกแบบไว้เป็นเอกสาร

**สรุปเรื่อง A:** เหมือนวันแรกที่เริ่ม แทบไม่มีอะไรเปลี่ยนในแง่สินค้าจริง

### เรื่อง B — โครงสร้างพื้นฐานเบื้องหลัง (แทร็กภายในทีม) — มีความคืบหน้าจริง

ทีมทำสำเร็จและพิสูจน์แล้วจริง (มีหลักฐานทดสอบรองรับ):
- ฐานข้อมูลจริงบน Supabase มี 7 ตาราง เปิดระบบป้องกันข้ามร้าน (RLS) แบบบังคับ
- ทดสอบแยกข้อมูลร้านสำเร็จ (ร้าน A เห็นแค่ของตัวเอง ร้าน B เข้าถึงของร้าน A ไม่ได้)
- มี domain จริง (n8n และ War Room) ใช้งานได้แล้วในระดับทดสอบ
- เครื่องมือภายในทีม 3 ตัว (เข้าถึงข้อมูล/นับการใช้/บันทึกมอนิเตอร์) พร้อมเทสต์
- War Room (ห้องประชุมทีม AI) ทดลองประชุมจริงแล้ว 1 ครั้ง

**สิ่งสำคัญที่ต้องเข้าใจ:** งานกลุ่ม B นี้คือ **"ส่วนประกอบ"** ที่จะเอาไปใช้สร้างสินค้าจริงในอนาคต **ยังไม่ใช่ตัวสินค้าเอง** — มีฐานข้อมูลพร้อมแล้ว ไม่ได้แปลว่ามีบอทที่ลูกค้าคุยได้แล้ว เหมือนมีท่อน้ำพร้อมแล้ว ไม่ได้แปลว่าบ้านมีน้ำใช้แล้วถ้ายังไม่ต่อก๊อกน้ำ

### ทำไมสองเรื่องนี้ดูสับสนได้ง่าย

เพราะทีมทำงานสองแทร็กพร้อมกัน (ตามที่ออกแบบไว้ว่าแทร็ก B ไม่ต้องรอแทร็ก A) แทร็ก B บังเอิญคืบหน้าเร็วกว่า ทำให้ถ้าอ่านผ่านๆ จะรู้สึกว่า "มีอะไรเสร็จเยอะแล้ว" — แต่สิ่งที่นับเป็น "โครงการสำเร็จ" ต้องดูที่แทร็ก A (เรื่อง A) เท่านั้น เพราะนั่นคือสิ่งที่ทำให้มีรายได้จริง

## 10. ถ้า AI ยังงงหลังอ่านนี้ ให้ทำแบบนี้

1. เช็คว่าอยู่ที่ branch `phase-a-market-test-pivot` ไม่ใช่ `main`
2. อ่าน `docs/warroom/AI_OPERATING_PROTOCOL.md` ก่อนไฟล์อื่นเสมอ (มีฉบับไทยคู่กันคือ `.th.md`)
3. เช็ค `PROJECT_STATE.md` ว่าตอนนี้สร้างอะไรเสร็จจริงแล้วบ้าง (แยกจากที่ออกแบบไว้)

## 11. อัปเดตล่าสุด (26 ก.ย. 2569) — สิ่งที่เกิดขึ้นหลังจากสรุปฉบับแรก

เพิ่มส่วนนี้เพราะมีเหตุการณ์สำคัญเกิดขึ้นหลังจากไฟล์นี้ถูกเขียนครั้งแรก ทั้งเรื่อง git ที่พลาดเกือบเสียงาน และเรื่องโครงสร้างทีมที่ยังไม่นิ่ง

### 11.1 บทเรียนจากการ merge/push ที่เกือบพลาด — ต้องจำไว้

**เหตุการณ์:** ตอนจะ push การแก้ไข (`PROJECT_STATE.md`, `TASKS.md`, ระเบียบ AI) เข้า branch `phase-a-market-test-pivot` เจอปัญหาซ้อนกันหลายชั้น:
1. Branch เดียวกันมี 2 สาย commit แยกกันบนเครื่องกับบน GitHub (non-fast-forward)
2. มีไฟล์ค้างอยู่ 14 รายการใน branch ทำงานหลัก (`dev-workspace`) ที่ต้อง stash ก่อนจะสลับ branch ได้
3. **ระหว่างที่ stash อยู่ มีอีก session/หน้าต่างหนึ่งเข้ามาแก้ไฟล์เดียวกัน (`.opencode/agents/project-lead.md`) พร้อมกัน** โดยไม่มีใครรู้ตัว — สาเหตุจริงคือ**เจ้าของโครงการเปิดหลายหน้าต่างสั่งงานพร้อมกัน**ไม่ใช่ AI หลุดออกนอกระบบ

**ผลลัพธ์:** แก้ได้สำเร็จโดยไม่มีข้อมูลหาย เพราะ AI ทำถูกทุกจุด: หยุดทันทีที่เจอสัญญาณผิดปกติ (เวลาของไฟล์ไม่ตรงกับที่คาด), ไม่ force push, สำรองข้อมูลก่อนแก้ไขทุกครั้ง, ถามเจ้าของก่อนตัดสินใจสำคัญ

**กฎที่ต้องยึดต่อจากนี้:**
- **ถ้าสั่งงานหลายหน้าต่างพร้อมกัน ต้องแยกให้ชัดว่าหน้าต่างไหนแตะไฟล์/branch ชุดไหน** ห้ามให้สองหน้าต่างแตะไฟล์เดียวกันโดยไม่รู้ตัว
- `git stash push` ต้องใช้ `-u` (หรือระบุชื่อไฟล์ตรงๆ) เพื่อไม่ให้ไฟล์ใหม่ที่ยัง untracked หลุดไป
- Commit ต้องแยกตามเจ้าของงานจริง ไม่ยัดรวมไฟล์จากคนละ session/การ์ดเป็น commit เดียว
- ไฟล์ runtime ใหม่ (เช่นใน `services/**`) ต้องผ่าน reviewer คนละโมเดลก่อนถือว่าเสร็จเสมอ ไม่มีข้อยกเว้น
- ตรวจว่า repo มี `.gitignore` ก่อน `git add -A` แบบกว้างบน branch ไหนก็ตาม กันหลุดไฟล์ลับ (`.env`) โดยไม่ตั้งใจ

### 11.2 ระเบียบ AI Operating Protocol ได้รับการพิสูจน์แล้วว่าใช้งานได้จริง

ตลอดเหตุการณ์ข้อ 11.1 ทีม AI แสดงพฤติกรรมตรงตามระเบียบทุกจุด:
- หยุดถามเจ้าของทุกครั้งที่เจอจุดเสี่ยง (NEEDS_OWNER_DECISION) แทนที่จะเดาแล้วทำต่อ
- ปฏิเสธคำสั่งของเจ้าของโครงการเองเมื่อคำสั่งนั้นขัดกับหลักฐานจริง (เช่น ตอนกรอกใบคะแนน พบว่าตัวเลข "ผ่านรอบแรก" ที่เจ้าของบอกมาไม่ตรงกับบันทึกจริง ก็แก้ให้ถูกต้องแทนที่จะกรอกตามที่บอก)
- ตรวจซ้ำด้วยตัวเอง ไม่เชื่อรายงานของอีก AI ตัวเฉยๆ (เช็ค `git status`/`git diff` เองทุกครั้งก่อนสรุปว่า "ตรงตามแผน")
- Reviewer ทำ negative control (ทดสอบว่าถ้าไม่มีการแก้ไข test จะ fail จริง) ไม่ใช่แค่เขียน assert ผ่านลอยๆ

**สรุป:** ระเบียบนี้ไม่ใช่แค่เอกสารสวยงามอีกต่อไป มีหลักฐานจริงว่าใช้ได้ ควรยึดต่อไปเป็นมาตรฐาน

### 11.3 คำถาม 6 ข้อที่ยังรอคำตอบจากทีม — สำคัญมาก อย่าลืม

ระหว่างตรวจสอบรายงานสรุปโรดแมพที่ทีมส่งมา (`ROADMAP_STUDY_DRAFT_2026-09-26.md`) พบจุดที่ต้องเจ้าของโครงการตัดสินใจเอง ไม่ใช่ให้ทีมตัดสินใจแทน — **ส่งคำถามไปแล้ว ยังไม่ได้รับคำตอบ ณ เวลาที่เขียนสรุปนี้:**

1. `services/core` (FastAPI) ใช้รันบอทลูกค้าจริงหรือใช้แค่เครื่องมือภายในทีม (War Room/model gateway)?
2. Supabase ตัดสินใจเป็น production host แล้วหรือยัง หรือยังเป็นแค่ dev/test?
3. ตำแหน่งงานที่ทีมใช้จริง (researcher, builder, ops, security, model-recruiter/HR, reviewer, advisor) ตรงกับ `docs/warroom/ROLES.md` เดิม (Developer, MCP tool builder, Auditor, Cost Guard, Onboarding, Support, Marketing, Model Scout) หรือไม่ — ถ้าไม่ตรง ต้องอัปเดต `ROLES.md` ให้ตรงกับความจริง
4. ด่าน audit ใหญ่ (GA — ต้องผ่านก่อนรับลูกค้ารายแรก) ใครเป็นคนอนุมัติให้เพิ่มด่านนี้เข้าไปในแผน
5. ยอดเครดิต OpenRouter ปัจจุบันเท่าไหร่แน่ (เอกสารมีตัวเลขขัดกันเอง $1.19/$1.60/$1.82) — และ PL (ตำแหน่งหลักในทีม AI) **ยังไม่มีโมเดลสำรอง** ขัดกับ `docs/product/MODEL_POLICY.md` ที่กำหนดว่าทุกระดับต้องมี fallback
6. แผนงาน P0-P3/G1-G5 (พร้อมด่าน GA) ที่ทีมเสนอมา จะใช้แทน `docs/warroom/STARTUP_PLAYBOOK.md` เดิมไปเลยหรือไม่ — ถ้าใช่ ต้องรวมเป็นไฟล์เดียว ไม่ปล่อยให้มี 2 แผนขนานกัน

**ห้ามเดินหน้าตัดสินใจเรื่องใหญ่ต่อ (เช่น push งานแทร็ก B, เปิด PR, ขยับด่าน GA) จนกว่าจะได้คำตอบ 6 ข้อนี้ครบ**

### 11.4 ระบบความจำหลายแผนก — ของใหม่ที่กำลังจะติดตั้ง

เมื่อมีหลายแผนกทำงานพร้อมกัน (researcher, builder, ops, security, model-recruiter, reviewer, advisor) ความเสี่ยงคือแต่ละแผนกเขียนบันทึกคนละที่แล้วไม่มีใครรู้ว่าไฟล์ไหนเก็บอะไร — กำลังจัดวางระบบนี้:

- **`docs/project-memory/INDEX.md`** — ดัชนีกลาง บอกว่าไฟล์บันทึกไหนของแผนกไหน ทุก session ต้องอ่านก่อนเสมอ
- **กฎเหล็ก: แผนกหนึ่งเขียนได้แค่ไฟล์บันทึกของตัวเอง** ห้ามแก้ไฟล์บันทึกของแผนกอื่น เรื่องข้ามแผนกให้เขียนลง `decision-log.md` แทน (ป้องกันปัญหาแบบ `project-lead.md` ชนกันในข้อ 11.1 ไม่ให้เกิดซ้ำ)
- **รูปแบบบันทึกมาตรฐานเดียวกันทุกแผนก:** วันที่/เวลา — แผนก — หัวข้อ, ผู้เข้าร่วม, คุยเรื่อง, ตัดสินใจ, ค้างไว้, ทำต่อ
- ไฟล์นี้ (`PROJECT_BRIEF.th.md`) ควรถูกเพิ่มเข้า `INDEX.md` ด้วย เป็นจุดเริ่มอ่านอันดับแรกสำหรับ session ใหม่ที่ยังไม่รู้จักโปรเจกต์เลย

### 11.5 สิ่งที่ AI ทุกตัวควรรู้เพิ่มจากรอบนี้

- **repo จริงตอนนี้ขยายไปไกลกว่าที่ระบุในหัวข้อ 1-10 ของไฟล์นี้มาก** มีระบบ `.opencode/agents/*`, `services/core/`, `docs/project-memory/` ที่ไม่ได้ออกแบบไว้แต่แรก — ถือเป็นพัฒนาการที่ทีมต่อยอดเอง ไม่ใช่เรื่องผิด แต่ต้องรอคำตอบข้อ 3 (เรื่องตำแหน่งงาน) ก่อนถือว่าเป็นทางการ
- **แทร็ก B (เครื่องมือภายในทีม)** เดินหน้าไปไกลกว่าแทร็ก A (บอทลูกค้าจริง) มาก — ยังไม่ผิดกฎที่ว่า "แทร็ก B ไม่ใช่ด่านบังคับก่อนขาย" แต่ควรระวังไม่ให้งานแทร็ก B กินเวลาจนแทร็ก A ไม่ขยับ
- **ยังไม่มีอะไรถูก push ขึ้น GitHub จากงานแทร็ก B ทั้งหมด** (4 commit ค้างอยู่ใน `dev-workspace`) — รอคำตอบ 6 ข้อก่อนตัดสินใจว่าจะ push/เปิด PR หรือไม่
