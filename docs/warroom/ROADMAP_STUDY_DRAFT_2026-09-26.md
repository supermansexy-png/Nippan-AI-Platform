## 1. บทสรุปผู้บริหาร

ทุกฝ่าย "งง" เพราะโครงการเดินสองทางพร้อมกันโดยไม่มีแผนเดียวที่ทุกคนเห็นตรงกัน:
(ก) **เส้นทางลูกค้า** — บอท AI ตอบลูกค้าปลายทางให้ธุรกิจเล็กไทย ผ่าน LINE เป็นหลัก ราคา 299 บาท/เดือน
(ข) **เส้นทางเครื่องมือภายในทีม AI** — War Room, ที่ปรึกษาวางแผน (advisor), จัดทีมโมเดล, จ่ายงานผ่าน Git

เอกสารนี้รวบทั้งสองทางไว้ที่เดียว แยกชัดว่าอะไร "มีจริงแล้ว" / "ยังไม่มี" / "รอพี่ตัดสิน" พร้อมโรดแมพแบบลำดับเวลา (เป็นสัดส่วน ไม่ใช่วันที่จริง) และจุด go/no-go

**ข้อสรุปหลัก:** สิ่งที่ขวางการขายให้ลูกค้ารายแรก **ไม่ใช่โค้ดที่ยาก** แต่คือ **(1) ช่องทางแจ้งเตือนเจ้าของ, (2) การทดสอบ backup/restore กับฐานข้อมูลจริง, (3) ด่าน PDPA/สัญญา (ข้อความยินยอม / ลบข้อมูล / ระยะเวลาเก็บ)** ส่วนเครื่องมือภายในเป็นงานแยก ไม่ใช่ด่านของลูกค้า

## 2. ขอบเขต: "โครงการนี้" = ทั้งหมดของ repo นี้

| แทร็ก | คืออะไร | สถานะ |
|---|---|---|
| **A. เส้นทางลูกค้า (customer launch)** | บอท AI ตอบลูกค้าปลายทางให้ธุรกิจไทย ผ่าน LINE เป็นหลัก | ยังไม่เริ่มเป็นชิ้นเป็นอัน (มีเฉพาะรากฐานบางส่วน) |

## 4. สถานะปัจจุบัน (จากหลักฐานใน repo)

**มีจริงและยืนยันได้ (VERIFIED):**
- ผลิตภัณฑ์ Phase A = บอท AI ตอบลูกค้าปลายทางให้ธุรกิจเล็กไทย **299 บาท/เดือน/บอท** เหมา (ที่มา: `docs/product/PRICING_V1.md`)
- ฐานข้อมูล **7 ตาราง `lite_*`** บน Supabase จริง เปิด **RLS แบบ FORCE** ครบ (policy role `nippan_runtime`; login role `nippan_n8n` เป็นสมาชิกและไม่ bypass RLS)
- **แยกข้อมูลผู้เช่าพิสูจน์แล้วบน n8n จริง:** A เห็นตัวเอง = 1 / B เห็น = 0 / เขียนข้ามผู้เช่าถูกปฏิเสธ (42501) — `docs/n8n/T-030-execution-evidence.md`
- HTTPS: `https://n8n.nippan.org` และ `https://warroom.nippan.org` (หลัง Cloudflare Access — พี่ล็อกอินผ่านแล้ว)
- เครื่องมือภายใน 3 ตัว (data-access / usage-tracker / monitor-log) พร้อมเทสต์
- War Room ทดลองประชุมจริง 1 ครั้ง (เข้าใช้ + ห้อง + ต้นทุน ~$0.00015) และโค้ดจัดการวาระจากหน้าเว็บเสร็จ+ตรวจแล้ว (**ยังไม่ deploy**)

**ยังไม่มี / ยังไม่พิสูจน์ (INFERRED / UNKNOWN):**
- **ช่องทางแจ้งเตือนเจ้าของ** — โค้ด `monitor_log.py` ข้ามเงียบเมื่อไม่มี channel; ไม่เคยส่ง event แดงถึงเจ้าของ → **บล็อกงานบอท LINE**
- **backup/restore กับ Supabase จริง** — มีสคริปต์ ทดสอบแค่ DB ในเครื่อง
- **บอท LINE ต้นจนจบ** — ยังไม่มีโค้ด (ไม่มี bot/channel/handoff ในเทสต์)
- **ด่าน PDPA:** ข้อความยินยอมครั้งแรก, เส้นทางลบข้อมูลปลายทาง, สัญญาผู้เช่า (controller/processor), ระยะเวลาเก็บยืนยัน — ยังไม่ทำ/ยังไม่ยืนยัน
- **ไม่มี pipeline ปล่อยเวอร์ชัน** (deploy มือ) และไม่มี backup job ที่รันจริง
- **ทีมยังไม่ได้รับ config ใหม่ครบ** (ต้อง restart opencode) — สังเกตจากบทบาท security ที่เรียกไม่ได้

## 5. บันทึกการประชุมคณะศึกษา — ความเห็นแต่ละฝ่าย + จุดไม่ตรงกัน

### 5.1 researcher — ข้อเท็จจริง (มีข้ออ้างเกินจริง 3 จุด — PL แก้)
เสนอ: Phase A = บอท LINE บน n8n + ฐานข้อมูล · ราคา 299 บาท/เดือน · ด่าน playbook Steps 0–3
ชี้ว่า `ROADMAP.md` เป็นพิมพ์เขียวเก่าที่เก็บถาวร; trigger ที่เอกสารระบุ = "เมื่อมีผู้เช่า 25–30 รายที่ต่ออายุ/ทำกำไรได้ ค่อยพิจารณาเปิด Phase B"
- ❌ researcher ว่า "ระบบแจ้งเตือนแดงทำงานได้" → **ขัดหลักฐาน:** โค้ดข้ามเงียบ + ไม่เคยทดสอบถึงเจ้าของ → **คณะยึดหลักฐาน = ยังไม่มี**
- ❌ researcher ว่า รากฐาน n8n "ยังรอตัดสิน" → **ไม่ถูกต้อง** การพิสูจน์ n8n→Supabase เสร็จแล้ว
- ❌ researcher ว่า โฮสต์เป็น PostgreSQL self-hosted → จริงคือ **Supabase managed** (นักวิจัยระบุเองในหัวข้อข้อขัดแย้ง)

### 5.2 builder — ประมาณแรงงาน (ทั้งหมด **INFERRED**)
โค้ดที่มีจริง: `services/core` (FastAPI + War Room + model gateway), `services/dev/tools`, UI War Room
ไม่มีโค้ด n8n ใน repo (workflow อยู่บน instance), migration 9 ไฟล์, เทสต์ core 20 ไฟล์
น้ำหนักงานหลัก: adapter LINE, web-fetch/file-reader, onboarding (§7)

### 5.3 ops — hosting/CI/backup/monitoring (ส่งกลับบางส่วน 4/6)
- n8n + Supabase + Render preview + Cloudflare Access **มีจริง** (VERIFIED)
- **ไม่มี release pipeline** (deploy มือ); CI มี 2 workflow ไม่มี deploy/backup/schedule job
- backup มีแค่สคริปต์; restore ทดสอบเฉพาะ DB ในเครื่อง; **กับ Supabase จริงยังไม่ทดสอบ**
- monitoring มีดีไซน์ แต่ **ไม่มี alert ถึงเจ้าของจริง** และไม่มี backup job ที่รันจริง
- **provider decision ค้าง (NEEDS_OWNER_DECISION):** production host (VPS), n8n self-host vs hosted, Supabase managed vs self-host
- *(ส่วน "งาน ops ก่อนเปิดลูกค้า" และ "critical path" ถูกตัด — PL ประมาณจาก §7 แทน)*

### 5.4 security (ตัวแทน `opencode/nemotron-3-ultra-free`) — ด่านความปลอดภัย/ความเป็นส่วนตัว (ไม่ใช่คำแนะนำทางกฎหมาย)
- **แยกข้อมูลผู้เช่า:** ทุกตารางมี `tenant_id` + `bot_id` กรองทุกคิวรี่ (VERIFIED)
- **RLS:** FORCE บน 7 ตาราง ผูก `nippan_runtime` (VERIFIED)
- **residual ต้องปิดก่อนเปิดจริง:** role superuser (`BYPASSRLS`) / ฟังก์ชัน `SECURITY DEFINER` อาจข้าม RLS; ไม่มี rate limit กับ agenda writes
- **กุญแจ service-role:** `channels.credential_ref` เก็บแค่ reference ไม่เก็บ token (VERIFIED); secret อยู่ใน n8n credential store
- **auth fail-closed:** ทุก authorizer คืน `False` ทุก exception/mismatch (VERIFIED)
- **ด่านที่ยังไม่ทำ:** ข้อความยินยอมครั้งแรก, เส้นทางลบข้อมูลปลายทาง, สัญญา controller/processor, ระยะเวลาเก็บยืนยัน (UNKNOWN)
- **ห้ามเด็ดขาด:** ใช้ข้อมูลสนทนาเทรนโมเดลโดยไม่ยินยอมแยก · ข้อมูลข้ามผู้เช่า · บอทอ้างเป็นมนุษย์ · เปิดเผยชื่อโมเดล/ผู้ให้บริการ · เอา raw text ผู้เช่าเป็น system instruction · ให้คำแนะนำการแพทย์/กฎหมาย/การเงิน

### 5.5 model-recruiter (HR) — โควต้าโมเดล/งบ
- **OpenRouter เหลือ ~$1.19** (เอกสารขัดกันระหว่าง $1.19/$1.60/$1.82 → **ยังไม่ยืนยันสด**)
- **OpenCode Go:** เหมาจ่าย **$10/เดือน**; โควต้าแยกต่อโมเดล (5 ชม. 20% / สัปดาห์ 50% / เดือน 100%)
- `opencode-go/kimi-k3` โควต้าน้อย (~490 requests/เดือน) → เก็บไว้ตรวจงานสำคัญ
- **PL ไม่มี provider fallback อัตโนมัติ** — หมดเครดิต OpenRouter แล้ว PL หยุด
- **ห้ามส่งความลับ/ข้อมูลจริง** ให้โมเดลเทรน/เก็บ log 30 วัน (muse-spark 1.2/1.3, gpt-6-luna, gpt-5.6-luna, grok-4.6/4.7)

## 6. จุดที่คณะไม่ตรงกัน (disagreement) + หลักฐานที่ขาด

| ประเด็น | ฝ่ายหนึ่งว่า | อีกฝ่าย/หลักฐาน | ข้อสรุปคณะ |

## 11. ความเสี่ยงสำคัญ (เรียงตามผลกระทบ)
